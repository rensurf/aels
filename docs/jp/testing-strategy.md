# テスト戦略

「何をテストすべきか」の判断基準。毎回迷わないためのガイド。

---

## 一言で言うと

**ロジックをテストする。配管工事（I/O）はテストしない。**

テストの目的はバグを仕込みやすい場所に安全網を作ること。
バグが入りにくい場所にテストを書いても、モックを検証しているだけで実際の動作を保証しない。

---

## テストを書く判断基準

次のどれかに当てはまればテストを書く：

1. **条件分岐がある** — 入力によって結果が変わる
2. **数値計算がある** — 計算ミスが起きうる
3. **エッジケースが明確** — 境界値でバグが起きやすい
4. **リファクタ時に壊れる可能性がある** — 回帰テストとして意味がある

---

## テストを書かない判断基準

次のどれかに当てはまればテストは不要：

1. **ロジックがない** — `return f"Saved {len(phrases)} phrase(s)"` のような1行
2. **モックを検証しているだけ** — 「DBを1回呼んだか」を確認しても実際の動作を保証しない
3. **フレームワーク・ライブラリの動作** — Agent が何回ツールを呼ぶかはGPT-4oの判断でありテストできない
4. **外部サービスのラッパー** — Gremlin/DynamoDB/OpenAI の呼び出し自体はサービス側の責任

---

## このプロジェクトの具体例

### 書く価値がある

| 対象 | 理由 |
|---|---|
| SM-2 アルゴリズム (`algorithm.py`) | 数値計算 + 条件分岐あり。ease_factor の更新ロジックは間違えやすい |
| Gremlin クエリ生成 (`queries.py`) | 文字列操作 + エスケープ処理。アポストロフィ1つでクエリが壊れる |
| `is_duplicate_update` | 重複 / 非重複の分岐 + DynamoDB 例外ハンドリングあり |

### 書かなくていい

| 対象 | 理由 |
|---|---|
| `save_phrases` の戻り値 | ロジックなし。Python の return 文が動くかを確認するだけ |
| DynamoDB の呼び出し回数 | モックの検証。実際の挙動を保証しない |
| Agent のツール呼び出し挙動 | GPT-4o の判断。単体テストで制御できない |
| Gremlin / DynamoDB の接続成功 | インフラの問題。単体テストのスコープ外 |

---

## テストの種類と使い分け

| 種類 | 対象 | このプロジェクトでの使い方 |
|---|---|---|
| **単体テスト** | 純粋な関数・ロジック | SM-2, クエリ生成, 重複チェック |
| **ローカル Agent テスト** | Agent の挙動確認 | `test_agent_local.py` で実際に動かして確認 |
| **本番確認** | 外部サービスとの結合 | Telegram でメッセージを送って確認 |

---

## カバレッジ目標について

カバレッジ数値（80% など）はあくまで目安。
重要なのは「意味のあるテストが書かれているか」であり、カバレッジを上げるためだけのテストは書かない。

> High coverage with bad tests is worse than low coverage with good tests.
> Bad tests give false confidence.
