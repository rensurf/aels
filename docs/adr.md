# AELS v2: Architecture Decision Records (ADR)

設計過程で検討した選択肢、メリット・デメリット、最終判断をまとめたドキュメント。
「なぜこの設計にしたか」を説明できる状態にするために作成。

---

## ADR-001: コンセプト — ツールか先生か

### 背景
v1は「フレーズを保存→復習するツール」として設計された。数週間で使わなくなった。

### 検討した選択肢

**A) ツール（v1の延長）**
- ユーザーが能動的に操作する
- 保存・復習の手動フロー
- メリット: シンプル、実装が明確
- デメリット: 使い続けるモチベーションが続かない。v1で証明済み。

**B) 自分専用の英語の先生**
- 先生に話しかけるイメージ
- 向こうから来る（プロアクティブ）
- Renの癖を覚えていて、強みも弱点も把握している
- メリット: 使い続ける動機が生まれる。習慣化しやすい。
- デメリット: 実装の複雑さが上がる

### 決定: B）先生
v1の失敗の本質は「保存の設計」ではなく「使い続ける体験の設計」がなかったこと。
ツールではなく先生というコンセプトに変えることで、プロダクトの軸が変わる。

## ADR-002: 保存の仕組み — 自動保存か選択保存か

### 背景
v1は「保存して」と言わなければならない場面があり、それが地味なストレスだった。
v2では自動保存を検討した。

### 検討した選択肢

**A) 完全自動保存**
- 会話の中から自動でフレーズを検出して保存
- メリット: ユーザーの操作ゼロ
- デメリット: 何でも保存されてしまう。覚えたいものと覚えなくていいものの区別がない。

**B) ユーザーが選んで保存**
- 複数の候補を提示し、ユーザーが選ぶ
- メリット: 自分が「覚えたい」と思ったものだけ入る。学習効果が高い。
- デメリット: 操作が必要

**C) 会話から傾向・パターンを自動抽出（保存はしない）**
- フレーズは保存しないが、会話のやり取りから弱点・強みを自動的に蓄積する
- メリット: 意識せずに先生がRenを「観察」できる
- デメリット: フレーズとして復習できない

### 決定: B + C の組み合わせ
- フレーズの保存はユーザーが選ぶ（B）
- 同時に、会話のやり取り自体から傾向・弱点・強みを自動抽出してグラフに蓄積（C）
- 「保存したい」という明示的な行動と、「先生が観察する」という暗黙的な蓄積を両立する

## ADR-003: ストレージ — DynamoDB vs PostgreSQL vs グラフDB

### 背景
v1はDynamoDBを使っていたが、v2では設計をゼロベースで見直した。

### 検討した選択肢

**A) DynamoDB（v1から流用）**
- メリット: AWSネイティブ、サーバーレス、スケール
- デメリット: 集計クエリ（弱点分析）が苦手。再帰的な関係の表現が複雑。v2のユースケースに向いていない。

**B) PostgreSQL（Neon / Supabase）**
- メリット: SQLで集計クエリが書きやすい。SM-2スケジューリングも自然に書ける。無料。
- デメリット: 多段トラバーサル（A→B→C→D）は再帰CTEが複雑になる。

**C) グラフDB（Azure CosmosDB Gremlin API）**
- メリット: 多段トラバーサルが得意。「エラー→パターン→根本原因→関連フレーズ」という連鎖的な検索が自然に書ける。先生の「賢さ」はつながりから生まれるため、グラフ構造が本質的に合っている。実務経験あり。
- デメリット: PostgreSQLより運用コストが上がる。専用DBのため学習コストあり。

**D) Amazon Neptune**
- メリット: AWSネイティブのグラフDB
- デメリット: コストが高く$5/月の予算を大幅に超える。

### 決定: C）Azure CosmosDB（Gremlin API）のみ、PostgreSQLは使わない
このシステムの主なクエリパターンは多段トラバーサルであり、グラフDBが最適。SM-2スケジューリングデータもフレーズノードのプロパティとして持たせることでCosmosDBに統合できる。個人ツールのデータ規模では範囲クエリのパフォーマンス問題は発生しない（ADR-016参照）。実務でCosmosDBの運用経験があるため、運用リスクが低い。

## ADR-004: インターフェース — どのメッセージングプラットフォームか

### 背景
先生とのやり取りと、プロアクティブな通知の両方に対応できるインターフェースが必要。

### 検討した選択肢

**A) LINE**
- メリット: 日本では最も普及。Renが頻繁に使うアプリ。v1から継続。
- デメリット: オーストラリアではほぼ使われていない。移住後に使えなくなるリスク。Bot APIの表現力が限定的。

**B) Telegram**
- メリット: Bot APIが個人開発者向けに設計されており、審査なしで即日開発できる。InlineKeyboard・Markdownなど表現力が高い。世界中で使える（オーストラリア移住後も問題なし）。
- デメリット: 日本での普及率が低い。現時点では新たにインストールが必要。

**C) WhatsApp**
- メリット: オーストラリアで広く使われている。移住後の定着率が高い。
- デメリット: Business API経由でのみ自動送信が可能。Meta審査・ビジネス認証が必要。24時間ルール（ユーザーの返信後24時間以内しかメッセージを送れない）。テンプレートメッセージはMetaの事前承認が必要。1通あたりコスト発生。個人のカスタムボットには設計されていない。

**D) Slack**
- メリット: エンジニアに馴染みがある。フォーマットが豊富。
- デメリット: プライベートな学習には重い。ワークスペースが必要。

**E) Web UI**
- メリット: 自由度が高い。どこでも動く。
- デメリット: 別途アプリを開く必要があり、習慣化の障壁が高い。プッシュ通知が難しい。

### 決定: B）Telegramから始め、アダプターパターンで拡張できる設計にする
最初にTelegramを選んだ理由はBot APIの開発しやすさと世界対応。
将来的にWhatsAppへの移行も想定し、コアとアダプターを分離する設計にする。

```
[Core Layer]  先生のロジック（プラットフォーム非依存）
      ↓
[Adapter Layer]  Telegram / WhatsApp / LINE
```

## ADR-005: クラウド — AWSかAzureかマルチクラウドか

### 背景
CosmosDB（Azure）を使うと決めた時点で、残りのインフラをどこに置くかを検討した。

### 検討した選択肢

**A) フルAzure（CosmosDB + Azure Functions + Event Grid）**
- メリット: 一つのクラウドで完結。運用がシンプル。Azure Functionsは実務経験あり。
- デメリット: オーストラリアのスタートアップではAWSが主流。ポートフォリオとしてAWSの経験が示せない。

**B) フルAWS（Lambda + EventBridge + Neptune）**
- メリット: AWSで統一できる。AU求人市場に強い。
- デメリット: Amazon NeptuneはグラフDBだが、コストが高く予算超過。CosmosDBの実務経験が活かせない。

**C) マルチクラウド（Azure CosmosDB + AWS Lambda / EventBridge）**
- メリット: 「最適なツールを用途ごとに選ぶ」という実践的な判断を示せる。AWSの経験（AU求人向け）とAzureの経験（実務での強み）を両方ポートフォリオで示せる。Terraformで両方を統一管理できる。
- デメリット: クロスクラウドの認証・ネットワーク設定が増える。単一クラウドより運用が複雑。

### 決定: C）マルチクラウド
- グラフDB: Azure CosmosDB（技術的に最適、実務経験あり）
- コンピューティング: AWS Lambda + EventBridge（AU求人市場での認知度、実務と差別化）
- IaC: TerraformでAzure・AWS両方を管理（マルチクラウドの複雑さを吸収）
- 現職でAzure Functionsを使っているため、ポートフォリオではAWS Lambdaを使うことで新しいスキルを示す

## ADR-006: IaC — TerraformかCDKかBicepか

### 検討した選択肢

**A) Terraform**
- メリット: AzureとAWS両方を管理できる。オーストラリアの求人市場での標準。マルチクラウドを扱えることがスキルとして示せる。
- デメリット: HCLの学習コスト。状態管理（tfstate）が必要。

**B) AWS CDK**
- メリット: Pythonで書ける。AWSリソースのタイプセーフな定義。
- デメリット: AWSのみ。Azureの管理には使えない。

**C) Azure Bicep**
- メリット: Azureネイティブ。シンプル。
- デメリット: Azureのみ。AWSの管理には使えない。

**D) AWS SAM**
- メリット: Lambdaに特化。シンプル。
- デメリット: 汎用性が低い。Azureに対応しない。

### 決定: A）Terraform
マルチクラウド構成（Azure + AWS）の管理にはTerraformが唯一の現実的な選択肢。
AU求人市場での標準でもあるため、ポートフォリオ価値も高い。

## ADR-007: LLM — 単一モデルかマルチLLMか

### 背景
v1でClaudeを使っていたが、ChatGPTの方が英語が自然に感じる場面があった。また、「なぜそうなるか」という理由の説明ではGeminiが秀逸という個人的な実体験もある。

### 検討した選択肢

**A) Claude一本**
- メリット: シンプル。すでにAPIアクセスあり。
- デメリット: v1での実体験として「ChatGPTの方が自然に感じた」という信頼の問題が残る。今回の用途（英語表現・説明）でClaudeを使う場面がそもそも少ない。

**B) GPT-4oのみ（シンプル構成）**
- メリット: 自然な英語生成が得意。APIキー1つ、課金先1つ。シンプル。
- デメリット: 「なぜ？」系の説明がGeminiより弱い場面がある。

**C) マルチLLMルーティング（GPT-4o + Claude）**
- メリット: 用途ごとに最適なモデルを使える。
- デメリット: Claudeをこの用途で使う場面が実体験として少ない。複雑さに見合わない。

**D) マルチLLMルーティング（GPT-4o + Gemini）**
- 表現・翻訳・添削 → GPT-4o（自然さ優先）
- 「なぜ？」系の説明・理由・ニュアンスの違い → Gemini（説明の深さ優先）
- メリット: 「表現を出す能力」と「理由を説明する能力」をモデルの得意不得意で分担できる。ルーティングシグナルが「なぜ・どうして・理由・違いは？」というキーワードで明確に拾えるため、シンプルなルールベースで実装できる。UXドリブンな判断。
- デメリット: APIキー2つ、課金先2つ。ただしClaudeより実体験に基づいた選定。

### 決定: まずB）GPT-4oのみで始め、実使用の中で判断する

初期フェーズでマルチLLMの複雑さを持ち込むのは過剰。まずGPT-4o一本で動かし、「ここは別モデルの方がいい」と感じた場面が出てきた時点でルーティングを追加する。

**追加候補モデルと想定用途：**
- Gemini: 「なぜ？」系の理由説明（個人的な実体験ベース）
- Claude: 英語の自然さ・散文の質（ベンチマーク上の評価あり。v1での不満は当時のモデルバージョンによる可能性も）

**将来的なルーティング追加時の設計：**
- ルーティングシグナル: 「なぜ」「どうして」「理由」「違いは」「なんで」などのキーワードベース（ルールベースで十分、LLMによる事前分類は不要）
- デフォルト: GPT-4o

## ADR-008: エージェントフレームワーク — 使うかどうか、使うなら何か

### 背景
「先生」の実装にエージェントフレームワークが必要かどうかを検討した。

### 検討した選択肢

**A) エージェントフレームワークなし（シンプルなPythonサービス）**
- メリット: 理解しやすい。無駄がない。
- デメリット: マルチターンの文脈保持、動的なツール呼び出し、複数ステップの推論をすべて自前で実装する必要がある。

**B) LangChain**
- メリット: 有名。事例が多い。
- デメリット: API変更が多く学習コストが高い。過去に不安定さで問題になった事例あり。

**C) Microsoft Agent Framework（旧Semantic Kernel + AutoGen統合）**
- メリット: 実務経験あり。マルチエージェント対応。エンタープライズグレード。MCP・A2Aプロトコル対応。2026年4月にv1.0 GA。
- デメリット: このユースケースに対して過剰な部分もある。

**D) 直接API呼び出し（フレームワークなし）**
- メリット: 最もシンプル。依存関係が最小。
- デメリット: フレームワーク知識がポートフォリオで示せない。

### エージェントフレームワークが正当化される部分
以下の動きはルールベースのif/elseでは書けず、フレームワークが有効：
- 翻訳・添削の会話（マルチターン・コンテキスト保持）
- LLMのルーティング判断（文脈を読んで推論）
- グラフ検索→関連フレーズ取得→説明生成の複数ステップ

以下はシンプルなサービスで十分：
- SM-2スケジューリング（決定的な計算）
- クイズ配信（テンプレートベース）
- 弱点集計（SQLで完結）

### 決定: C）Microsoft Agent Framework（会話部分のみ）
実務経験があることによる運用リスクの低さと、マルチエージェント対応の拡張性を評価。v1.0 GAでプロダクション利用が可能になった。エージェント化するのは「先生との会話インターフェース」に絞り、バックグラウンド処理はシンプルなサービスとして分離する。

## ADR-009: メモリアーキテクチャ — 会話履歴をどう持つか

### 背景
ChatGPTのように全会話履歴をコンテキストに詰め込む方法では、やり取りが増えるにつれてコンテキストウィンドウが枯渇する問題がある。

### 検討した選択肢

**A) 全会話履歴をコンテキストに渡す（ChatGPT方式）**
- メリット: 実装がシンプル
- デメリット: 会話が増えるにつれてコンテキストが重くなる。やがてバカになる。長期的な学習ツールとして成立しない。

**B) 直近N件のみを渡す（スライディングウィンドウ）**
- メリット: コンテキストが一定サイズに収まる
- デメリット: 古い情報（過去に覚えたフレーズ、弱点など）が失われる。先生としての記憶が消える。

**C) RAGベースの長期記憶（グラフ + サマリー）**
- 会話は都度グラフ・DBに保存
- 新しい質問が来たとき、関連する過去情報のみを取得してコンテキストに注入
- Renのプロフィール（強み・弱点・ゴール）をサマリーとして常時保持
- メリット: コンテキストウィンドウを常に軽い状態に保ちながら、先生は長期記憶を持てる。グラフ構造と自然に統合できる。
- デメリット: 実装の複雑さが上がる。「何を取得するか」の設計が重要。

### 決定: C）RAGベースの長期記憶
長期的に使い続けることがこのシステムの前提であり、会話が増えても劣化しない設計が必須。
知識グラフへの蓄積とRAGによる取得を組み合わせることで、先生が「本当に記憶を持つ」体験を実現する。
詳細設計は別途。

## ADR-010: メモリアーキテクチャ詳細 — セッションサマリー・取得ロジック・書き込みタイミング

### 背景
ADR-009でRAGベースの長期記憶方針を決定した。本ADRではその詳細設計を決定する。

---

### ADR-010-A: セッションサマリーの形式

#### 検討した選択肢

**A) 構造化データのみ（フレーズ＋弱点パターン）**
- グラフのノード・エッジとして整理されたデータだけを保存する
- メリット: グラフトラバーサルの精度が高い。定量的な弱点分析ができる。ストレージが軽い。
- デメリット: 「なぜこの表現を選んだか」という文脈の再現ができない。会話レベルの連続性が失われる。

**B) 構造化データ＋要約テキスト（ハイブリッド）**
- フレーズ・弱点パターンのグラフ保存（A）に加えて、セッションの要点を自然言語のサマリーとして保存する
- 例: 「ビジネスメールの添削をした。受動態が2箇所あり、能動態に直した。丁寧さとカジュアルさのバランスについて質問があった。」
- メリット: Aのメリットをすべて保ちつつ、PatternConnectionの精度が上がる。「似た状況」の過去情報をRAGで引けるようになる。先生が「先日と同じシチュエーションですね」と言える。
- デメリット: サマリー生成のコストが毎セッション発生する（セッション終了後の非同期処理にできるためユーザー体験には影響しない）。LLMによる要約のため情報の取捨選択が発生する。

**C) 生の会話履歴を保存**
- やり取りそのものをDBに保存する
- メリット: 完全な再現性
- デメリット: 履歴が増えるにつれてノイズも増え、RAGの取得精度が落ちる。コストも高い。

#### 決定: B）構造化データ＋要約テキスト（ハイブリッド）
先生らしい連続性（「先日と同じシチュエーションですね」）はBで実現できる。Cの複雑さとコストを避けつつ、Aより豊かな文脈情報を保持できる。サマリー生成はセッション終了後の非同期処理として実装する。

---

### ADR-010-B: 取得ロジック

#### 検討した選択肢

**A) 直近N件のサマリーを取得**
- 新しいリクエストが来たら直近のセッションサマリーをN件引いてくる
- メリット: 実装がシンプル。「最近の流れ」を先生が把握できる。
- デメリット: 意味的な関連付けができない。「今日のメール添削」に対して「3ヶ月前の類似添削」を引けない。

**B) グラフトラバーサルで取得**
- リクエストのキーワード・分類からグラフを辿り、関連ノード（フレーズ・弱点パターン・コンテキスト）を取得する
- メリット: PatternConnectionの中核。「これと同じパターンを以前も間違えた」が言える。構造的なつながりに基づく検索。
- デメリット: 意味的な曖昧さへの対応に限界がある（「ビジネスメール」と「フォーマルな文章」を同一視するにはエッジの事前設計が必要）。

**C) ベクトル検索で取得（Pinecone等）**
- セッションサマリー・フレーズをベクトル化しておき、意味的に近いものを引いてくる
- メリット: 意味レベルで「似た状況」を検索できる。グラフに事前定義していない関係も発見できる。
- デメリット: 「なぜ関連しているか」の説明ができない（ベクトル検索は「近い」は分かるが「どう近いか」は分からない）。PatternConnectionの説明にはグラフが必要。Pineconeの追加管理コストが発生し$5/月の制約に影響する。

**D) B＋Cのハイブリッド**
- 構造的なつながりはグラフ、意味的な類似はベクトル検索で補う
- メリット: 最も豊かな検索
- デメリット: 実装複雑さとコストが大幅に上がる。初期フェーズでは過剰。

#### 決定: B）グラフトラバーサル（将来的にDへ拡張可能な設計にする）
CosmosDBグラフだけでPatternConnectionの中核は実現できる。ベクトル検索はグラフで拾えない関連性が実際に問題になった時点で追加する。Pineconeの追加コストも先送りできる。

---

### ADR-010-C: 書き込みのタイミング

#### 検討した選択肢

**A) セッション終了後にバッチで書き込み**
- 会話が終わった後、まとめてグラフを更新しサマリーを生成する
- メリット: シンプルな実装。やり取り中にDBアクセスが発生しないのでレスポンスが速い。
- デメリット: セッション中の弱点検知ができない（「今の会話でこのパターンが3回目ですね」とリアルタイムに言えない）。

**B) リアルタイムで書き込み（各ターンごと）**
- 各ターンごとにグラフを更新する
- メリット: セッション中の弱点検知が可能
- デメリット: 各ターンでDBアクセスが発生しレスポンスが遅くなるリスク。途中でセッションが切れた場合の整合性管理が必要。

#### 決定: A）セッション終了後にバッチで書き込み
「先生が次のセッションで気づく」で十分なユースケースがほとんど。リアルタイム検知は実装複雑さに見合わない。初期フェーズではAで進め、必要を感じた時点でBへの移行を検討する。

## ADR-011: コンテキスト分類の体系 — 知識グラフのコンテキスト軸

### 背景
知識グラフのフレーズノードに「どの場面で使うか」を持たせることで、Goal-Aware Teachingの精度が上がる。その分類体系の粒度と設計を決める。

### 検討した選択肢

**A) 粗い固定カテゴリ（3〜4種類）**
- 例: `職場` / `日常` / `フォーマル` / `感情表現`
- メリット: シンプル。Goal-Aware Teachingの基本的な分岐が作れる。
- デメリット: 「オーストラリア職場」と「一般職場」の区別ができない。文化的ニュアンスが消える。

**B) 細かい固定カテゴリ（多数）**
- 例: `AU職場` / `一般職場` / `友人` / `フォーマルメール` / `SNS` / `感情表現` / `独り言` / `技術`
- メリット: 細かい文脈に合った表現提案が可能。
- デメリット: フレーズが少ない初期フェーズでは各カテゴリのデータが薄くなりPatternConnectionが機能しない。カテゴリの境界が曖昧になりやすい。

**C) タグベース（複数付与可）**
- フレーズに複数タグを付けられる。例: `"No worries, will do"` → `[AU職場, カジュアル, 口語]`
- メリット: 一つの表現が複数の文脈に属せる。グラフ上でタグをクラスタとして扱える。拡張が柔軟。
- デメリット: タグ定義を事前にある程度決めないと一貫性が崩れる。

**D) 最初は定義せず、使いながら育てる**
- メリット: 過設計を避けられる。実際に溜まる表現を見てから分類できる。
- デメリット: Goal-Aware Teachingが初期から機能しない。コンテキストなしでは「オーストラリアの職場では〜」が言えない。

### 決定: C）タグベース、初期タグ定義はAの粒度から始める

タグベースの構造を採用し、初期タグは `職場` / `日常` / `フォーマル` / `感情` の4種類で始める。`AU職場` のような細分化は実際に必要を感じた時点で追加する。タグ付けはLLMに任せず、フレーズ保存時に先生が判断するメタデータとして管理する。

## ADR-012: Telegramインターフェース設計 — 自由テキストかコマンドか

### 背景
「先生に話しかける」というコンセプトに対して、Telegramでのインターフェースをどう設計するかを決める。

### 検討した選択肢

**A) 自由テキストのみ**
- コマンドなし。何でも自由に送ればいい。
- メリット: 「先生に話しかける」コンセプトと完全に一致する。学習の動線がシンプル。
- デメリット: 先生がリクエストの意図を毎回推測する必要がある。意図が曖昧な場合に追加の往復が発生する。

**B) コマンドベース（/translate・/review 等）**
- `/translate 承知しました` のように意図を明示する。
- メリット: LLMへの指示が明確になり、応答の精度が安定しやすい。
- デメリット: 「先生に話しかける」体験が失われる。ユーザーがコマンドを覚える必要がある。v1の「操作する」感覚に戻ってしまう。

**C) 自由テキストをベースに、任意のコマンドも使える**
- 基本は自由テキスト。慣れてきたユーザーが `/review` のような明示的な指定もできる。
- メリット: 自然な会話体験を保ちながら効率化できる。先生が意図を読み間違えた時のリカバリーになる。
- デメリット: コマンドとの共存設計がやや複雑になる。

### 決定: A）自由テキストのみで始める

「先生に話しかける」コンセプトを守るならAが正解。意図が曖昧なときは先生が聞き返す設計にする（それ自体が先生らしい挙動）。コマンドはCのように後から追加できるため、初期から設ける必要はない。

## ADR-013: クイズの回答形式 — 選択式か自由入力か

### 背景
SM-2スペースドリピティションで復習クイズを出す際、どう答えてもらうかを決める。

### 検討した選択肢

**A) 選択式のみ（InlineKeyboard）**
- 4択などの選択肢をTelegramのボタンで提示する。
- メリット: 操作が一タップで完結。スキマ時間に気軽にできる。正誤の判定が確実。
- デメリット: Recognition（見て選ぶ）にとどまり、Recall（思い出す）が鍛えられない。なんとなく選べてしまう場合がある。

**B) 自由入力のみ**
- 「この表現を英語で書いてみて」とテキストで答えてもらう。
- メリット: Recallの練習になる。思い出すプロセスが定着に直結するという学習科学的な根拠がある。
- デメリット: 回答のハードルが上がりスキマ時間に億劫になりやすい。採点にLLMによる自然言語判定が必要で実装が複雑。

**C) 両方（習熟度で使い分け）**
- 新しいフレーズや苦手なものは選択式、定着したものは自由入力に切り替える。
- メリット: 学習フェーズに合った形式。SM-2の習熟度スコアと連動できる。
- デメリット: 実装の複雑さが上がる。切り替え閾値の設計が必要。

### 決定: A）選択式で始め、将来的にC）へ育てる

v1の失敗は習慣化できなかったことが本質。まず「続けられる」体験を作ることが最優先であり、最初のハードルは下げる。習熟度データが溜まった段階でCへの移行を検討する。

## ADR-014: Teaching Style Adaptationのデータ設計

### 背景
先生がRenさんの「学び方の癖」を覚えて教え方を変える機能。例文が好きか、理由から入る方が理解が早いか、などをグラフ上にどう持つかを決める。

### 検討した選択肢

**A) Renのプロフィールノードにフラットなプロパティとして持つ**
- 例: `prefers_examples: true` / `asks_why_often: true`
- メリット: 実装がシンプル。プロフィール取得が一発で済む。
- デメリット: 傾向の変化を追跡できない。「最近は例文より理由を先に聞くことが増えた」という変化が見えない。

**B) 観察イベントをエッジとして積む**
- 「例文を求めた」「なぜ？と聞いた」などのイベントを都度エッジとして記録し、傾向は集計から導く。
- メリット: 傾向の変化を追跡できる。「最近3ヶ月」vs「全体」の比較も可能。
- デメリット: データが溜まらないと機能しない。毎回集計クエリが必要。

**C) セッションサマリーに含めてRAGで取得**
- Teaching Styleを独立ノードとして持たず、セッションサマリーの一部として保存しRAGで引く。
- メリット: ADR-010の設計と自然に統合できる。別途グラフ設計が不要。
- デメリット: 「Renの学び方の傾向」として定量的に集計・可視化できない。週次レポートで傾向を伝えるのが難しくなる。

### 決定: A）プロフィールノードのプロパティで始め、将来的にB）へ育てる

Teaching Style AdaptationはWeek 3以降の機能であり、初期から複雑な設計は不要。まずプロパティとしてシンプルに持ち、データが溜まってきた段階で観察イベントのエッジを追加して精度を上げる。

## ADR-015: Pythonバージョン — 3.11 vs 3.12 vs 3.13

### 背景
バックエンドのPythonバージョンを決める。

### 検討した選択肢

**A) Python 3.11**
- メリット: 枯れていて安定。ライブラリ互換性の問題が起きにくい。
- デメリット: 3.12と比べてサポート期限が短い（2027年10月まで）。パフォーマンス改善も3.12に劣る。新規プロジェクトで選ぶ積極的な理由がない。

**B) Python 3.12**
- メリット: 安定していて本番実績が十分にある。AWS Lambdaの公式ランタイムとして対応済み。Semantic Kernel・CosmosDB GremlinクライアントSDKなど主要ライブラリの互換性が確認されている。サポート期限が2028年10月まで。
- デメリット: 最新版ではない。

**C) Python 3.13**
- メリット: 最新機能（実験的なfree-threaded mode等）が使える。
- デメリット: 2024年10月リリースでまだ新しく、本番での実績が少ない。AWS LambdaのPythonランタイムへの公式対応やライブラリのエコシステムが追いついていないリスクがある。

### 決定: B）Python 3.12

新規プロジェクトでは「安定していて、使うスタック（Lambda・Semantic Kernel・CosmosDB SDK）との互換性が確認されている最新版」を選ぶのが基本。3.13は本番実績とエコシステムの成熟を待ってから検討する。

## ADR-016: ストレージ統合 — PostgreSQLを追加するか

### 背景
SM-2スケジューリングデータの保存先としてPostgreSQLが候補に上がっていた。CosmosDB（Gremlin）に統合できるか検討した。

### 検討した選択肢

**A) PostgreSQLを追加（CosmosDB + PostgreSQL）**
- メリット: SQLで集計・範囲クエリが書きやすい。SM-2の計算データとの相性が良い。
- デメリット: 管理するサービスが増える。コストが上がり$5/月の制約に影響する。個人ツールのデータ規模では過剰。

**B) CosmosDBに統合（グラフのみ）**
- SM-2データ（next_review_date・ease_factor・interval）をフレーズノードのプロパティとして持たせる。復習対象の取得は `g.V().hasLabel('phrase').has('next_review_date', lte(today))` で対応。
- メリット: アーキテクチャがシンプル。管理サービスが1つ。コスト最小。
- デメリット: グラフDBは範囲クエリに最適化されていない。ただし個人ツールのデータ規模（フレーズ数百〜数千）では問題にならない。

### 決定: B）CosmosDBに統合

個人ツールのデータ規模ではCosmosDBのプロパティ検索で十分。PostgreSQLを追加することで得られるのは「SQLの書きやすさ」だけであり、コスト増・運用複雑化に見合わない。「CosmosDBで十分だと判断してPostgreSQLを外した」という設計判断はポートフォリオとしても説明できる。

## ADR-017: Lambda をまたいだ会話状態の永続化

### 背景

Agent Framework の `session` オブジェクトはインメモリであり、Lambda の実行が終わると消える。Telegram のメッセージは別々の webhook 呼び出しとして届くため、`chat_id` と `session` を跨いで会話状態を永続化する仕組みが必要。

ADR-009・ADR-010 が扱う「長期記憶（知識グラフ）」とは別問題。こちらは「一連の会話フロー（例: 翻訳→どちら保存する？→両方）」を複数の Lambda 呼び出しにまたいで保持するための短期ストレージ。

**保存すべき内容:**

```
chat_id (PK) | messages (直近の会話履歴) | pending_choices | last_activity | TTL
```

**各 Lambda 呼び出しのフロー:**

```
① DynamoDB から chat_id で messages を取得
② 新しい Agent Framework session を作成
③ 過去 messages を session に注入
④ agent.run(新しいメッセージ, session=session)
⑤ 更新した messages を DynamoDB に書き戻す
```

### 検討した選択肢

**A) DynamoDB（TTL付き）**
- メリット: サーバーレス、VPC不要、AWS 同一エコシステム、Terraform が aws provider だけで完結、無料枠で十分カバー
- デメリット: Redis より API が冗長（boto3）、レイテンシは 1-10ms（Redis より遅い）

**B) Redis（ElastiCache）**
- メリット: サブミリ秒レイテンシ、TTL ネイティブ
- デメリット: VPC 必須 → Lambda コールドスタートに +100-500ms、常時起動で $15-30/月（予算超過）

**C) Redis（Upstash）**
- メリット: サーバーレス Redis、VPC 不要、HTTP ベースで Lambda と相性良し、無料枠あり
- デメリット: 新規サービス追加（Terraform に upstash provider が必要）

**D) Agent Framework の Service-managed storage（OpenAI 管理）**
- OpenAI API がサーバー側で会話状態を保持し、`service_session_id` だけを保存する方式
- メリット: 自前で messages を管理しなくていい。実装が最もシンプル
- デメリット: OpenAI への依存が強まる。会話履歴の自社管理ができなくなる。将来的な LLM 切り替えの障壁になる

### Agent Framework 公式ドキュメントの位置付け

公式ドキュメント（https://learn.microsoft.com/en-us/agent-framework/agents/conversations/storage）によると、外部ストレージ（Redis・DB・Blob）を使う場合は「Third-party/Custom storage pattern」として自前の history provider を実装する。Redis は言及例として挙げられているが、ファーストパーティの Redis アダプターは提供されておらず、DynamoDB も同様にカスタム実装が必要。どちらを選んでも実装量は同じ。

### 決定: A）DynamoDB（TTL 24時間）

ボトルネックは GPT-4o（2〜5秒）であり、セッション読み書きの 1ms vs 10ms の差はユーザー体験に影響しない。Upstash Redis も有力な選択肢だが、DynamoDB は AWS 同一エコシステムかつ Terraform 追加 provider が不要でシンプル。Redis の速度優位がこのユースケースで意味を持つようになった時点で移行を検討する。

## ADR-018: Webhook 応答戦略 — 同期か非同期か

### 背景

Telegram は webhook に 30 秒以内のレスポンスを要求する。GPT-4o 呼び出し + Gremlin クエリを含む処理は 5〜15 秒かかる可能性がある。処理完了まで 200 を返さない場合、Telegram がリトライを発行しメッセージが重複する。

### 検討した選択肢

**A) 完全同期（処理完了後に 200 を返す）**
- メリット: 実装がシンプル。Lambda 1 つで完結
- デメリット: GPT + Gremlin で 10 秒超えると Telegram がリトライ → メッセージ重複。ユーザー体験として無音の待ち時間が続く

**B) 即時 200 + Lambda 非同期 invoke**
- Webhook Lambda が即時 200 を返し、別の処理 Lambda を非同期で起動する
- メリット: リトライ問題が解決する
- デメリット: Lambda が 2 つ必要、IAM 設定が増える、ローカル開発が複雑になる。Week 1 のスコープとして過剰

**C) 即時「考えています...」送信 + 同期処理 + editMessageText**
- Webhook 受信後すぐに `sendMessage("考えています...")` を Telegram に送信
- Lambda timeout を 29 秒に設定して同期で処理
- 処理完了後に `editMessageText` で書き換え
- メリット: Lambda 1 つで完結。ユーザーに「処理中」が伝わる。リトライ問題も実質的に回避できる
- デメリット: `editMessageText` の実装が必要（ただし軽微）

### 決定: C）即時「考えています...」+ 同期処理

Week 1 のシンプルさを保ちながらユーザー体験を担保できる。Lambda 2 つ構成は Week 1 では過剰。処理が 29 秒を超えるようであれば B への移行を検討する。
