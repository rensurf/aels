# AELS — Autonomous English Learning System

[![CI](https://github.com/rensurf/aels/actions/workflows/ci.yml/badge.svg)](https://github.com/rensurf/aels/actions/workflows/ci.yml)

A full-stack English learning web app with a REST API backend (AWS Lambda + API Gateway), React/Vite frontend served via CloudFront, and DynamoDB — all provisioned with Terraform.

---

## Why I built this

I had already built v1 of this project: an MCP-based phrase saver. It worked. I stopped using it within weeks.

The failure wasn't technical. I had built a tool, not a product. I designed the save feature but never designed the experience of actually sticking with it. Phrases piled up with no review. Notifications arrived with no habit behind them.

v2 starts from the opposite direction. Before writing any code, I asked: *why didn't I keep using v1?* The answer was that the tool waited for me — I had to go to it. So v2 comes to me. It messages me for reviews. It remembers what I struggled with. It quizzes me on phrases I saved days ago.

The goal isn't a smarter flashcard app. It's a teacher that shows up.

---

## What it can do today

- **Flashcard review** — SM-2 spaced repetition scheduling; correct answers extend the interval, wrong answers reset it; streak tracking with a GitHub-style activity calendar
- **Phrase manager** — CRUD for saved phrases with type classification (sentence / phrasal verb / idiom / fixed phrase), usage notes, and alternative phrasings
- **Verb reference** — CRUD for verbs with OALD-based conjugation patterns generated by o4-mini (reasoning mode)
- **AI chat** — multi-turn conversational English tutoring powered by GPT-4o; thread history stored in DynamoDB; create and switch threads mid-session
- **Phrase analysis** — paste any phrase to get AI-generated type, note, and alternatives
- **Topics** — structured topic learning with bullet points, keyword extraction, quiz sessions, and correction tracking

## Architecture

```
Browser
   │
   ▼ HTTPS
AWS CloudFront
   │
   ├─ /api/* → AWS API Gateway → Lambda (Python 3.12)
   │                                   ├─ Phrases     GET/POST/PUT/DELETE /phrases
   │                                   ├─ Verbs       GET/POST/PUT/DELETE /verbs
   │                                   ├─ Chat        POST /chat  (GPT-4o, multi-turn)
   │                                   ├─ Threads     GET/POST /threads
   │                                   ├─ Review      POST /phrases/{id}/review  (SM-2)
   │                                   ├─ Stats       GET /stats  (streak, calendar)
   │                                   ├─ Analyze     POST /analyze  (AI phrase analysis)
   │                                   └─ Topics      CRUD + keywords + sessions + corrections
   │
   └─ /* → S3 (React/Vite static assets)

AWS DynamoDB
   — phrases     (SM-2 fields, type, note, alternatives)
   — verbs       (OALD-based patterns, sources)
   — threads     (GPT-4o chat history per thread)
   — user-stats  (streak, daily review counts)
   — topics      (bullets, keywords, corrections)
```

## Key Engineering Decisions

**Why DynamoDB instead of the original graph database?**

v2 used Azure CosmosDB's Gremlin API for a phrase knowledge graph. Graph traversal was a natural fit for SM-2 edge properties, but it introduced operational complexity: a separate Azure account, Gremlin query syntax, and cross-cloud latency. v3 moved all data to DynamoDB — SM-2 fields (`ease_factor`, `interval`, `due_date`) sit directly on each phrase item. This simplifies the stack to a single cloud, reduces cold-start latency, and makes the schema easier to extend.

**Why SM-2 for review scheduling?**

SM-2 is the algorithm behind Anki. It tracks per-phrase `ease_factor`, `interval`, and `repetitions`, and adjusts how soon you see a phrase again based on how well you answered. Correct answers push the interval out exponentially; wrong answers reset it. This concentrates review time where it's actually needed.

**Why o4-mini for verb conjugation?**

Verb conjugation analysis (OALD-based patterns, V5 adjective/past-participle disambiguation) benefits from step-by-step reasoning. o4-mini with `reasoning_effort=low` gives noticeably more accurate pattern generation than GPT-4o on this task at lower cost per call.

**Why AWS Lambda instead of a server?**

Traffic is bursty and unpredictable. Lambda scales to zero when idle (cost: $0) and scales out instantly on demand. API Gateway's HTTP API adds minimal overhead at lower cost than the REST API tier.

## Setup

### Prerequisites

- Python 3.12
- [`uv`](https://github.com/astral-sh/uv) package manager
- Node.js 20+
- Terraform
- AWS CLI configured (`aws configure`)

### 1. Install Python dependencies

```bash
uv venv
source .venv/bin/activate
uv pip install -r requirements.txt
```

### 2. Environment variables

```bash
cp .env.example .env
```

```bash
OPENAI_API_KEY=               # from platform.openai.com
WEB_API_KEY=                  # any string; sent as X-API-Key header from the web app
WEB_USER_ID=                  # your user ID stored in DynamoDB
DYNAMODB_PHRASES_TABLE=aels-phrases
DYNAMODB_VERBS_TABLE=aels-verbs
DYNAMODB_THREADS_TABLE=aels-chat-threads
DYNAMODB_STATS_TABLE=aels-user-stats
DYNAMODB_TOPICS_TABLE=aels-topics
AWS_REGION=ap-southeast-2
```

### 3. Deploy infrastructure

```bash
cd infrastructure/terraform
terraform init
terraform plan
terraform apply
```

### 4. Build and deploy frontend

```bash
cd web
npm install
npm run build
aws s3 sync dist/ s3://<your-bucket> --delete
aws cloudfront create-invalidation --distribution-id <id> --paths "/*"
```

### 5. Deploy Lambda

```bash
bash infrastructure/scripts/deploy.sh
```
